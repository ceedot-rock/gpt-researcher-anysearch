## 1. What the maintainer actually requires (verbatim)

Source: issue comment by **assafelovic** on PR #2203,
2026-11-09T10:15:42Z (fetched live via GitHub API 2026-11-11). PR #2203
was closed unmerged by the maintainer at 10:15:43Z the same day
(`merged: false`).

> "Thanks @ceedot-rock. New search providers now ship as their own package
> through the `gpt_researcher.retrievers` entry point instead of living in
> core, so each provider can release on its own schedule and users only
> install what they use. Keenable and Sciverse went this way: see
> [Retriever plugins](https://docs.gptr.dev/docs/gpt-researcher/search-engines/retriever-plugins).
> Once an AnySearch package is on PyPI, a docs PR adding it to the
> community retrievers table is very welcome. #2228 proposes the same
> integration, so I'm closing both in favour of a single package."

Spec from the linked Retriever plugins docs page (read in full 2026-11-11,
crawled <1 min before the read) and confirmed against upstream main
(assafelovic/gpt-researcher, cloned 2026-11-11):

- Plugin = a class with the same shape as built-in retrievers, registered
  under the `gpt_researcher.retrievers` entry-point group.
- Contract: `__init__(self, query, query_domains=None)`;
  `search(self, max_results=7)` returns a list of dicts, each with a URL
  under `href` (or `url`) and an optional `body` snippet.
- `requires_scraping = True` unless results carry full page text under
  `raw_content`.
- Return `[]` on network/parsing errors instead of raising.
- Entry-point name = the value users put in `RETRIEVER`.
- Usage: `pip install gptr-acme-retriever`, `export RETRIEVER=acme`.
  Built-in names take precedence over plugins.
- Core discovery (verified in upstream source):
  `gpt_researcher/actions/retriever.py` — `get_retriever(name)` falls
  through to `_load_plugin_retriever(name)`, which loads
  `entry_points(group="gpt_researcher.retrievers", name=name)`; on import
  failure it logs a warning and falls back to the default retriever.
  `gpt_researcher/retrievers/utils.py` — `get_all_retriever_names()`
  returns built-in directory names PLUS plugin entry-point names.
- Core instantiation path: `skills/researcher.py:901` calls
  `retriever_class(query, query_domains=query_domains)`.
- Community table lives in
  `docs/docs/gpt-researcher/search-engines/retriever-plugins.md`
  ("Community retrievers"); current rows: Keenable
  (`gpt-researcher-keenable`), Sciverse (`gpt-researcher-sciverse`).

PR #2228 (Zhiyilang, also closed 2026-11-09) proposed the same
integration as a built-in retriever and claimed live calls worked against
the public API (anonymous general search + `code.doc` vertical). That
claim is theirs, not verified by this build — see §6 for this build's own
live results.

## 2. Decisions (each flagged where nothing was specified)

- **Package name `gpt-researcher-anysearch`, version 0.1.0.** The
  maintainer did NOT name the package. The name follows the two precedent
  packages the maintainer cited (`gpt-researcher-keenable`,
  `gpt-researcher-sciverse`), not the illustrative `gptr-acme-retriever`
  in the docs example. A PyPI name check on 2026-11-11 returned HTTP 404
  for `gpt-researcher-anysearch` — the name is free. Renaming before
  publish is a one-line change in `pyproject.toml`.
- **Entry-point name `anysearch`.** Matches `RETRIEVER=anysearch` from
  PR #2203; this is the registration string the docs contract requires.
- **Module `anysearch_retriever`, class `AnySearchRetriever`.** Same class
  name as PR #2203.
- **Subclasses `BaseRetriever`.** PR #2203's class was a plain class; the
  docs plugin example subclasses `BaseRetriever`. Subclassing matches the
  documented plugin shape exactly; the core treats it as optional. All
  behaviour is otherwise ported verbatim from PR #2203, commit `aebc6d2`
  (ceedot-rock/gpt-researcher branch `anysearch-retriever`): same endpoint,
  payload, headers, `X-Anysearch-Client: gpt-researcher-anysearch/1.0`,
  clamping 1–10, error branches, diagnostics (`last_error`,
  `last_request_id`).
- **License MIT**, matching upstream gpt-researcher's declared license
  (`license = { text = "MIT" }` in its pyproject). Copyright Corey Tasz 2026.
- **Dependency `gpt-researcher>=0.17.0`** (0.17.0 is the PyPI release and
  the upstream main version on 2026-11-11; the entry-point discovery code
  is present in it), plus `requests`.
- **Tag/params NOT reachable via `RETRIEVER=`.** The ported class accepts
  `tag`/`params` via constructor args and headers, exactly as PR #2203 did.
  The core only ever passes `(query, query_domains=...)`, so verticals are
  reachable only when constructing the retriever directly in Python. This
  gap is stated in the README and DOCS-PR-DRAFT.md; adding env-var routing
  (as PR #2228 did with `ANYSEARCH_TAG`/`ANYSEARCH_PARAMS`) would be a
  scope change beyond the faithful port, not done here.
- **Homepage URL in pyproject is the fork** (`ceedot-rock/gpt-researcher`,
  where the original PR lives). The standalone package repo does not exist
  yet; its URL is TBD at publish time and must replace this before upload.
- **No secrets anywhere:** no API key in code, tests, or logs (covered by
  the `test_no_key_in_logs_or_snapshots` test, passing).

Conclusion: the search endpoint was **unresponsive at ~10:15 EST**
(attempts 1–2: two timeouts, zero bytes) and **responsive by ~10:28 EST**
(attempts 3–4: two successes through the real class, anonymous, real
results with titles/URLs/snippets). The endpoint is intermittent or
recovered between the two windows — the two states are both measured and
both recorded. A successful live search is now **demonstrated twice**,
which ticks the acceptance item that was open since 2026-10-10. The
retriever's timeout branch (verified by attempts 1–2) and success path
